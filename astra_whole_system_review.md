## Verdict

**The shipping GT Harness is not proven to work end to end, and the paid arktype run is a failed product execution. Confidence: high.** It did run the certified graph producer, execute Mini-SWE, call the intended provider, inject real GT evidence, modify source files, and invoke the official verifier. It did not deliver a patch to that verifier, complete its native receipts, or produce a usable canonical feature audit. Its official zero reward is real, but the verifier explicitly graded the pristine base, not the agent's final edited workspace.

The largest demonstrated performance problem is synchronous graph rebuilding. The intervals from 38 invalidations to their following refreshes total **4,050.094 seconds**, against a 5,400-second agent phase. The intervals include intervening observation work and therefore are not a precise profiler measurement of producer CPU time; the synchronous call chain and approximately 99–166-second intervals nevertheless establish a major GT-imposed latency problem. Prompt replay is another large, independently demonstrated problem: 25,242,024 cumulative input tokens over 115 calls, including one tool result followed by a 117,223-token prompt increase.

**The initial timeout/token/dependency fixes were insufficient.** During this review the main agent also changed raw-output preservation, assistant-history compaction, refresh scheduling, patch export, capability declaration, and the indexing wrapper. Several are meaningful source repairs. The follow-up performance pass found that the wrapper's supposed contract-embedding refresh imports a nonexistent module-level function and silently does nothing; it is not a delivered embedding repair. None of these worktree changes constitutes a new successful installed-container run, a successful official grade, or demonstrated improvement over the retained baseline. Remaining blockers and the acceptance evidence needed to close them appear below.

There is no evidence that GT improved solve rate here. There is strong evidence that its refresh policy consumed solve time and its delivery policy crowded out more useful information. There is weaker evidence that the actual prose distracted the model; the visible next commands mostly continued the model's existing investigation, and hidden reasoning cannot establish causality. Do not replace that distinction with either “GT caused every failure” or “GT was harmless because its hints were advisory.”

### Why advisory is not the intended engine architecture

`eval/miniswe_agent.py` explicitly passes `--gt-mode advisory`; `build_agent` and `GTSessionConfig` default to it. `GTSession.model_visible` permits automatic evidence in advisory mode, so advisory does **not** mean GT was wholly off: the 19 real deliveries prove otherwise. However, `can_enforce` is false, `allows_live_probes` is false, `request_submit` chooses `advisory_submit_decision`, and the documented graph/context/catalog engine is not thereby connected. `GT_SUBMIT_SUPPRESSION_ENFORCE` or profile flags do not override these global mode checks. Conversely, merely changing the global mode to ENFORCED would not activate live probes: that property explicitly requires ASSISTIVE. The dimensions have been conflated.

The correct design separates (a) deterministic computation and automatic context, (b) permission and budgets for additional local checks, and (c) authority to block an action. Automatic graph/transaction context should operate at every eligible boundary in the supported GT-on mode. Extra verification may run only under declared scoped execution policy. Blocking requires current positive RED evidence and durable suppression authority; speculative graph candidates never become verification authority, and official task reward remains the official verifier's. The user requires a continuously active engine, not indiscriminate hard enforcement of advisory graph guesses. No inference about why a past author chose advisory can be established from code; the effective behavior is unambiguous.

**P1 producer cardinality/storage defect, high confidence.** The reference documentation describes a 458-file base checkout; this retained end-of-run graph has 487 `file_hashes` rows. It is not 2.679 GB of source intelligence. Its 461,376 nodes contain 283,101 `DerivationFact`, 136,017 `CompletenessFact`, 19,253 `Callsite`, 19,171 `UnresolvedFact`, two policy nodes and only 3,832 ordinary source/file nodes. The mechanism is concrete:

- Each candidate is represented in `resolution_candidates`, a `DerivationFact` node and three edge populations: **283,101 `CANDIDATE`, 283,101 `CANDIDATE_TARGET`, and 283,101 `HAS_DERIVATION_FACT`**. The graph has only 2,304 `CALLS` and 82 `SELECTED_TARGET` edges. These types have different semantics; neither edge count nor the historical 36% figure is a valid replacement for a well-defined current resolution-quality measure.
- **276,887 candidates (97.8%) use `name_match`; none of these candidate rows is selected.** The largest callsites have 103 possible targets for ubiquitous test names such as `it`. A group of 1,653 callsites with more than 100 candidates accounts for 169,268 candidates; another 1,434 with 11-100 accounts for 96,777. Unique constraints mean these are not duplicate `(callsite,target)` rows. The duplication is repeated ambiguous sets, per-candidate explanatory structures and repeated values across storage representations.
- `CANDIDATE` edge metadata contains **283,628,589 characters**, with **164,208,631 more** in `provenance_steps`. Inspection shows JSON repeating the callsite ID, target stable ID, build/source fingerprints, receiver/import fields and other values already present in columns or related rows. `HAS_CALLSITE.pass_coverage` alone contributes another 14,441,402 characters. Candidate `pass_coverage` is mostly `[]`, so the earlier pass-coverage repair does not solve candidate-set multiplication.
- Five completeness passes repeat across all 19,253 callsites, plus CHA/RTA/VTA/overload and legacy rows. `flow_fact_budget=512` is recorded, but `budget_abstained_callsites=0`, `budget_withheld_flow_facts=0` and `coverage_set_budget=0`. This budget demonstrably does not constrain the enormous name-match candidate representation in this graph.
- Source-symbol rows have **zero `/out/` paths**. Generated files explain unnecessary transaction/invalidation work in the old snapshotter, not this graph's dominant storage. They are separate repairs.

Root fix: retain truthful candidate-set semantics while storing common set/provenance/build data once in the **primary graph**, linked by compact references; narrow candidates with sound import/scope/type evidence before expansion; materialize high-detail explanations on the decision frontier; bound work and emit explicit incompleteness/abstention when necessary. Use partial/covering indexes justified by production queries. Do not silently drop candidates, lower trust thresholds, treat ambiguous names as resolved, or move the entire reasoning substrate into an unconsumed sidecar merely to report fewer primary rows. R27 requires measured output-quality and storage/latency conservation, not a cosmetic row-count reduction.

## Feasible graph lifecycle: what can ship now and what requires producer work

**Recommendation: one automatic decision engine over an immutable certified base plus revision-bound transaction overlay, with coalesced rebuilds. Confidence: high on required invariants; moderate on achievable latency until measured.** The latest `indexer.py::refresh_index_files` explicitly discards `graph` and `changed_paths` and calls a full `ensure_index_with_receipt`; it is not incremental despite its name. No sound complete affected-slice command is available through the shipping harness interface. Do not call the producer's older single-file functionality a replacement without proving candidate/derived completeness; the producer's own single-file logic acknowledges that repository-wide candidate parity cannot be certified from one file.

1. **At task start:** certify one immutable base graph and its exact HAR-69 reuse key. Bind repository source-manifest revision, graph-content revision, producer/schema identity and workspace revision in the same central runtime object. Reuse only on an exact key match. Contract embeddings must be either a primary graph-native service or explicitly an optional cache over primary facts with validated bindings, not an alternate authority.
2. **After every real edit:** persist the authoritative transaction immediately. Publish file content hashes, creates/deletes/renames, actual patch, supported syntax/signature delta, invalidated evidence/verification IDs and a dependency-risk classification before the next model decision. Do not wait for a repository rebuild to tell the model what it just changed. Retain exact unsupported/incomplete dispositions for languages the current extractor cannot parse.
3. **Selectively retain base facts:** unaffected source content/addresses can be revalidated by file hash. A history-only cochange fact may survive an edit if its history key and relevant paths still apply; label it prior, not current program semantics. Changed symbols' contracts/callers cannot remain certified. Global uniqueness, absent-definition claims, dynamic/configuration resolution, communities and transitive reach require broader invalidation where dependencies are not complete. An unchanged file alone does not prove its caller set unchanged: another file may add a call.
4. **At each task/open/view/edit/failure/verification/submit boundary:** the same orchestrator automatically composes a bounded context packet from current overlay plus eligible base claims, with source/graph/overlay revision, completeness, provenance and named omissions. It feeds the next actual Mini-SWE decision and records exact admitted bytes. If a necessary graph answer cannot be proven, return current local evidence and a named abstention; never silently stop all GT work or silently serve stale certainty.
5. **Coalesce full builds safely now:** maintain one latest desired revision and at most one background build per repository. Build from a frozen source snapshot/worktree, not a live tree that changes under the producer. Debounce batches of edits; trigger by explicit need for a global claim, accumulated dependency risk or a bounded freshness age, not simply every provider turn. Prioritize relevant work and respect the absolute deadline. Publish core/derived state atomically under a compare-and-swap of the requested revision; an obsolete build may be retained as an older valid snapshot but must not be advertised as the current workspace. Overlay changes newer than the published graph remain active.
6. **Producer work required for true incremental intelligence:** a certified API accepting changed files, old/new source identities and dependency closure; stable-symbol mapping; deletion/rename reconciliation; complete caller/import/configuration invalidation; separate derived-layer invalidation/rebuild receipts; bounded candidate-set refinement and atomic publication. Where complete affected-slice proof is unavailable, fall back to a bounded full rebuild or explicit partial result. No claim that a local Python AST delta provides complete TypeScript call-graph update.
7. **Finalization:** current patch and executed verification evidence outrank optional graph enrichment when time is low. A final full rebuild must not consume the patch/receipt reserve. Submit can carry partial/unavailable graph-derived checks honestly; official verifier remains grade authority. If required product-mode evidence is missing, the runtime reports that limitation rather than a verified finish.

This preserves the user's architecture: GT continuously provides the deterministic state and evidence that Mini-SWE uses to reason and act. It also preserves the soundness constraint: the full reusable artifact is invalidated by a source edit, but provably unaffected facts and current transaction facts remain useful through explicitly scoped identities. Neither rebuilding a 2.679 GB graph after each edit nor leaving it dormant/stale until a typed query is an acceptable final design.
