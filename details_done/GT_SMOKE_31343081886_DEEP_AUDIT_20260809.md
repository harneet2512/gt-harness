## Diagnosis and release decision

The implementation boundary and accounting are correct for this smoke. The
outcome gate is not: `write-compressor` exhausted its 900-second task budget
before a completion certificate/submit. Its receipt has no visible GT payload and
only one private obligations effect, so this loss cannot be attributed to a GT
guidance intervention from the available evidence. It is nevertheless a
treatment regression and blocks the 89-task run. The next investigation must
compare the write-compressor GT-on and GT-off trajectories at the first divergent
action and inspect deadline/completion-controller state before any new paid run.

An offline trajectory inspection already establishes that the first selected
write-compressor command differs between the frozen GT-off trajectory and this
GT-on trajectory (the baseline begins with a short `cat /app/decomp.c` read;
the treatment begins with a larger combined read of `decomp.c` and `data.txt`).
The treatment had no prior visible GT payload and applied no preflight
intervention, so this first divergence predates any GT-visible evidence. That
is consistent with temperature-1 trajectory variance, but it does not clear
later controller/context effects; the later deadline-reserve path still needs a
request/state diff before another smoke.

Decision: **integrity certified; outcome/efficiency gate rejected; 89-task run
blocked.**
